# Halqa Statement of Applicability

Reference HQ-IN-05. ISO/IEC 27001:2022 Annex A, all 93 controls.

For each control: whether it applies to Halqa, how it is met or why it does not apply, and where the evidence is. Written to be true on 6 October 2026, which is why most entries record a control as applicable and not yet in place.

A document claiming 93 controls in place at a company that is not yet incorporated, has no staff and has never held a board meeting would be worse than no document: the first thing a reviewer asks for is the evidence, and there would be none. The gaps are named instead, with what closes each one.

## Summary

| Status | Controls | Meaning |
| :-- | --: | :-- |
| In place | 22 | Built, and the evidence can be produced today |
| Partly | 36 | Some of it is built and the gap is named |
| Not yet | 16 | Applicable, nothing built |
| Not applicable | 19 | With the reason |

The three that matter most among those not yet in place are 8.16 monitoring, 5.24 incident response planning and 8.13 the untested backup restore. Each should close before the first member joins rather than before the first audit.

## 5. Organisational Controls

### 5.1 Policies for information security

Status: Not yet.

An information security policy is drafted but not yet approved: there is no board to approve it, because the company is not yet incorporated. The policy set is listed in section AL1 of the work register, and approval is the first board agenda item after incorporation.

Evidence: Draft policy set in 05 Governance; work register items for drafting, approval, publication and annual review.

### 5.2 Information security roles and responsibilities

Status: Partly.

One person builds and operates the service today, which is stated plainly rather than dressed as a structure. The roles a partner bank will require, including a named security officer, are allocated in the governance pack and take effect on incorporation.

Evidence: Governance pack; the register of roles in 05 Governance.

### 5.3 Segregation of duties

Status: Not yet.

Not achievable with one person, and saying otherwise would be false. The compensating control is that every change to production is recorded in version control and every money movement is recorded in the ledger and the audit log, so no action is unattributable even where it is not separated.

Evidence: Git history; AuditLog and LedgerEntry tables; src/lib/audit.ts.

### 5.4 Management responsibilities

Status: Not yet.

Depends on 5.1 and 5.2. The chairman holds the duty in the interim and the governance pack records it.

Evidence: Governance pack.

### 5.5 Contact with authorities

Status: Partly.

The regulator is identified and the route to it is understood: the State Bank of Pakistan supervises this activity, which the mentorship of 27 September settled, and the partner bank is the channel for anything requiring a licence. No incident reporting contact is yet registered because there is nothing yet to report.

Evidence: Regulatory position in 08 Regulatory and Legal; the bank partnership documents.

### 5.6 Contact with special interest groups

Status: Not yet.

No membership of a security forum or CERT yet. Worth doing once there is a company to join in its own name.

Evidence: Open item.

### 5.7 Threat intelligence

Status: Partly.

Dependency advisories are the only feed in use, through the package manager and the repository host. There is no paid feed and none is proportionate yet.

Evidence: npm audit output; repository security advisories.

### 5.8 Information security in project management

Status: Partly.

Security work is carried in the same work register as everything else rather than in a separate track, which is why sections AJ, AK and AL exist. Each item carries its owner and its file.

Evidence: Work register sections AJ, AK, AL.

### 5.9 Inventory of information and other associated assets

Status: In place.

Every record and every field is listed in the data dictionary, generated from the database schema itself so it cannot drift. Thirty nine records, six hundred fields, with the fields holding personal data marked.

Evidence: Data Dictionary (HQ-IN-04), generated by docs/generators/register_rev7/make_data_dictionary.py.

### 5.10 Acceptable use of information and other associated assets

Status: Not yet.

An acceptable use policy is drafted and unapproved, as 5.1.

Evidence: Draft policy set.

### 5.11 Return of assets

Status: Not applicable.

No employee or contractor holds an asset of the company. It becomes applicable at the first hire and is in the joining and leaving procedure for that day.

Evidence: Governance pack, joiners and leavers procedure.

### 5.12 Classification of information

Status: Partly.

The data dictionary marks which fields hold personal data and which hold a credential that never leaves the service. A full four tier classification scheme is not written.

Evidence: Data Dictionary, the Holds column.

### 5.13 Labelling of information

Status: Not yet.

Depends on 5.12.

Evidence: Open item.

### 5.14 Information transfer

Status: In place.

Everything the application sends travels over TLS, and HTTP Strict Transport Security is set with a six month maximum age including subdomains, so a browser will not fall back. The service returns only JSON and sets a content security policy that forbids scripts, objects and frames outright.

Evidence: src/app.ts, the helmet configuration: hsts maxAge 15552000, contentSecurityPolicy defaultSrc none.

### 5.15 Access control

Status: In place.

Every route requires a signed in member, and each one checks the specific right it needs before acting: membership of the circle, hosting of it, or ownership of the record. The checks were audited endpoint by endpoint and the exceptions are listed as deliberate.

Evidence: src/lib/guards.ts assertMember and assertHost; tests/api, 276 integration tests of which 93 assert refusal without access.

### 5.16 Identity management

Status: In place.

One account per person, keyed on a unique username, email, mobile and CNIC, and checked for all four at sign up. Identity is graded in levels: nothing on file, CNIC recorded, bank verified.

Evidence: prisma/schema.prisma unique constraints; src/routes/auth.ts register; kycLevel.

### 5.17 Authentication information

Status: In place.

Passwords are stored only as a bcrypt hash and never returned in any response. The application PIN is hashed the same way. The service refuses to start in production with a weak or default signing secret.

Evidence: src/lib/security.ts assertSecretsStrong; the SECRET column of the data dictionary, which lists exactly three secret fields; tests asserting no credential appears in any response.

### 5.18 Access rights

Status: Partly.

Member rights follow from membership and hosting and are checked on every route. Administrative rights are a single role flag, which is enough for one operator and will not be enough for a team.

Evidence: requireAdmin in src/lib/auth.ts; the role column.

### 5.19 Information security in supplier relationships

Status: Partly.

The suppliers are known and listed: the hosting provider, the database provider, the payment service provider, the credit bureau and the messaging provider. No security schedule is signed with any of them yet because no agreement is signed with any of them yet.

Evidence: Work register section AL7; the supplier list in 05 Governance.

### 5.20 Addressing information security within supplier agreements

Status: Not yet.

Evidence: Open item; heads of terms with the partner bank.

### 5.21 Managing information security in the ICT supply chain

Status: Partly.

Dependencies are pinned by exact version in the lock file, so a build cannot silently take new code. There is no formal review of a supplier's own suppliers.

Evidence: package-lock.json; the pinned devDependencies in package.json.

### 5.22 Monitoring, review and change management of supplier services

Whether that is acceptable under the State Bank's cloud framework is an open question put to the partner bank, and it is in the register as such rather than assumed.

### 5.28 Collection of evidence

Status: In place.

Every change of consequence is recorded with the actor, the action, the record it touched and the time, and the writes that matter are now inside the same transaction as the change they describe, so a change cannot exist without its entry.

Evidence: AuditLog table; src/lib/audit.ts; the thirty two write pairs wrapped in transactions on 6 October.

### 5.29 Information security during disruption

Status: Not yet.

No continuity plan is written and no recovery objective is set.

Evidence: Open item.

### 5.30 ICT readiness for business continuity

Status: Partly.

The hosting and database providers both carry their own redundancy, and the application is stateless so it can be redeployed from version control in minutes. The database restore has never been rehearsed, which is the part that matters and the part that is missing.

Evidence: Deployment configuration; provider documentation. No restore test on record.

### 5.31 Legal, statutory, regulatory and contractual requirements

Status: In place.

The legal position is written out against the primary texts, each clause verified against the statute rather than a summary of it, including the Payment Systems and Electronic Fund Transfers Act, the Banking Companies Ordinance, the Companies Act and the Insurance Ordinance.

Evidence: 08 Regulatory and Legal; the legal verification of 24 and 25 September.

### 5.32 Intellectual property rights

Status: Partly.

All third party code is open source and its licences are permissive. No licence review document exists.

Evidence: package.json dependency list.

### 5.33 Protection of records

Status: In place.

Retention is set per record class in the data dictionary, with ten years for anything a bank must keep and shorter periods for operational records.

Evidence: Data Dictionary, the Retention line on every record.

### 5.34 Privacy and protection of personal information

Status: Partly.

Personal data is marked field by field, consent is recorded and can be withdrawn, and no bureau report is requested without the member's instruction. A privacy notice exists in draft. There is no data protection officer and no personal data register beyond the dictionary.

Evidence: Data Dictionary; /api/profile/consent; the consent clauses of the undertaking.

### 5.35 Independent review of information security

Status: Not yet.

No independent review has been held. The partner bank's own review will be the first, which is the right order: paying for a review before the design is settled buys an opinion about a design that will change.

Evidence: Open item.

### 5.36 Compliance with policies, rules and standards for information security

Status: Partly.

The standing checks are automated and run on every change: a screen audit over 73 files, a contrast audit over 40 pairs of colours in both themes, an event audit, and 637 tests. What is not automated is compliance with the policies, because the policies are not yet approved.

Evidence: halqa-web/tests/audit-screens.mjs, audit-contrast.mjs, audit-events.mjs; halqa-api test suite.

### 5.37 Documented operating procedures

Status: Partly.

The development and deployment procedure is written down and kept current. The operational procedures a live service needs, including the collection run and the month end, are not.

Evidence: HANDOVER/MASTER-CONTEXT.md; the development runbook.

## 8. Technological Controls

### 8.1 User endpoint devices

Status: Partly.

The member's own device is not managed and cannot be. What the service does is require the application PIN on every open, record each signed in session as a device the member can see, and let them sign every other session out in one action.

Evidence: /api/account/devices; the PIN on open; src/routes/auth.ts set-pin and verify-pin.

### 8.2 Privileged access rights

Status: Partly.

The administrative role is required for the routes that need it, including the delinquency collector, which was open to any signed in member outside production until 6 October. Access to the hosting and database consoles is through one account with two factor authentication.

Evidence: requireAdmin usage; provider account configuration.

### 8.3 Information access restriction

Status: In place.

Each query is scoped to the caller: a member's own rows by their own id, a circle's rows through membership. The queries were audited for rows loaded wider than they are needed, and one was narrowed because it loaded a whole user row, credentials included, to read one score.

Evidence: The leak audit of 5 October; src/routes/protection.ts select narrowing.

### 8.4 Access to source code

Status: Partly.

The repository is private and access is through one account with two factor authentication. There is no branch protection and no review requirement, because there is one developer.

Evidence: Repository settings.

### 8.5 Secure authentication

Status: In place.

An account locks for fifteen minutes after five wrong attempts. Refresh tokens rotate on every use and a reused token burns the whole family of sessions descended from that sign in, which is what catches a stolen token. A malformed or expired token is refused as a sign in problem rather than reported as a service fault.

Evidence: src/routes/auth.ts refresh; the TOKEN_REUSE_REVOKED security event; tests/api/auth.test.ts.

### 8.6 Capacity management

Status: Partly.

Every list the service returns is bounded with a ceiling and a cursor, which is the capacity control that was missing: four endpoints returned every row a member had ever generated. There is no capacity forecast and no load testing.

Evidence: src/lib/page.ts; tests/page.test.ts; the bounds asserted over the wire in tests/api.

### 8.7 Protection against malware

Status: Partly.

The service runs no uploaded code and executes nothing a member sends. The development machine runs the operating system's own protection. Uploaded images are not scanned, which matters once a payslip or a CNIC photograph can be uploaded.

Evidence: Device configuration; the open item for scanning uploads.

### 8.8 Management of technical vulnerabilities

Status: Partly.

Dependency advisories are read and acted on. There is no scheduled scan and no penetration test.

Evidence: npm audit; repository advisories.

### 8.9 Configuration management

Status: In place.

Every configuration value is either in version control or an environment variable named in one place, and the service refuses to start in production without the ones that matter.

Evidence: src/lib/security.ts assertSecretsStrong; the environment variable list.

### 8.10 Information deletion

Status: Partly.

Retention is set per record class. The deletion itself is not yet automated, so nothing has been deleted on schedule because nothing has reached its schedule.

Evidence: Data Dictionary retention lines; the open item for the deletion job.

### 8.11 Data masking

Status: Partly.

Responses are narrowed to the fields a screen needs, and no response carries a credential. A member's CNIC and mobile are not masked where the member is looking at their own record, which is correct, and are not returned at all to anybody else.

Evidence: The response projections in src/routes; the reputation projection, which omits the CNIC.

### 8.12 Data leakage prevention

Status: Partly.

The audit over every response projection is the control in use: each one is read for fields that do not belong in it. There is no outbound monitoring.

Evidence: The leak audit of 5 October; tests asserting no credential in any response.

### 8.13 Information backup

Status: Partly.

The database provider takes automated backups on its own schedule. A restore has never been tested, which is the half that counts.

Evidence: Provider backup configuration. No restore test on record.

### 8.14 Redundancy of information processing facilities

Status: Partly.

The application layer is redundant by construction at the hosting provider. The database is a single instance.

Evidence: Deployment configuration.

### 8.15 Logging

Status: In place.

Three logs, each for its own purpose: the audit log for who changed what, the security event log for sign in and token events, and the ledger for every movement of money. Request logging carries the method, the path, the status and the duration and deliberately carries no member data.

Evidence: AuditLog, SecurityEvent and LedgerEntry tables; the request logger in src/app.ts.

### 8.16 Monitoring activities

Status: Not yet.

There is no error monitoring and no alerting at all, which the operational scan of 22 September found and which is still true. Nothing watches the service; a failure is noticed when somebody looks.

Evidence: Open item, and one of the few in this Statement that should be closed before the first member joins.

### 8.17 Clock synchronisation

Status: In place.

Every timestamp is set by the database or by the platform, both of which are synchronised, and all are stored in UTC. Nothing trusts a clock a client sends.

Evidence: prisma/schema.prisma default now(); the absence of any client supplied timestamp in the write paths.

### 8.18 Use of privileged utility programs

Status: Partly.

Database access outside the application is through one command line client on the development machine. There is no separate privileged tooling and no session recording.

Evidence: Device configuration.

### 8.19 Installation of software on operational systems

Status: In place.

Nothing is installed on a running system. A change reaches production only as a new deployment built from version control.

Evidence: Deployment configuration; git history.

### 8.20 Networks security

Status: Partly.

The service is reachable only over TLS and accepts cross origin requests from a named list of origins. The database is reachable only from the application. There is no network segmentation beyond what the providers give.

Evidence: src/app.ts cors origin list; provider network configuration.

### 8.21 Security of network services

Status: Partly.

Rate limits are set per route, tighter on sign in and on anything that sends a code or moves money, and keyed on the member when signed in and on the address otherwise. The address key collapses an IPv6 address to its prefix, without which a single subscriber could walk through billions of addresses and never reach a ceiling.

Evidence: src/lib/rate-limits.ts; tests/errors-and-limits.test.ts.

### 8.22 Segregation of networks

Status: Not applicable.

No network of the company's own exists to segregate. The providers segregate their own.

Evidence: Provider documentation.

### 8.23 Web filtering

Status: Not applicable.

No corporate network and no browsing on behalf of members.

Evidence: This Statement.

### 8.24 Use of cryptography

Status: In place.

Transport is TLS. Passwords and PINs are bcrypt. Tokens are signed and their stored form is a hash, so a stolen database row cannot be replayed as a session. Document signatures are recorded as a SHA-256 fingerprint of the exact text signed, which is what makes a signature evidence rather than a claim.

Evidence: src/lib/auth.ts; hashText in the agreements route; the textHash column.

### 8.25 Secure development life cycle

Status: Partly.

Every change is in version control, type checked, and run against 637 tests before it is considered done. There is no formal review step, because there is one developer.

Evidence: Git history; the test suite; the type check.

### 8.26 Application security requirements

Status: In place.

The security requirements are written as register items against each endpoint: schema checked input, sign in required, the specific access right checked, a rate limit, a shared error code, no internal field in any response, and three integration tests. They are tracked individually rather than as a heading.

Evidence: Work register section AE3.

### 8.27 Secure system architecture and engineering principles

Status: In place.

The principles are written down and enforced rather than described: money is recorded in a double entry ledger that must balance after every posting, a seat a member cannot sit in cannot be claimed by joining, trading or the ballot, and the rule lives in one engine that every path asks.

Evidence: src/lib/score-bands.ts and its 37 tests; the ledger identities in the split engine tests.

### 8.28 Secure coding

Status: Partly.

Input is validated by schema before any logic on every route, including the path. Database access is through a query builder, so no query is assembled from text. There is no coding standard document and no linter in the pipeline.

Evidence: src/lib/params.ts and tests/params.test.ts; the Prisma client; the schema parse at the head of each handler.

### 8.29 Security testing in development and acceptance

Status: Partly.

The suite includes tests that exist only to prove a refusal: 93 assert that an endpoint refuses a member without access, and others assert that no response carries a credential. There is no independent security test.

Evidence: tests/api; the access audit of 5 October.

### 8.30 Outsourced development

Status: Not applicable.

No development is outsourced.

Evidence: This Statement.

### 8.31 Separation of development, test and production environments

Status: Partly.

Development and production are separate deployments with separate databases, and the relaxed security switches used in development cannot be set in production. Test data is generated per run and never copied from production.

Evidence: The environment configuration; the production guards in src/lib/rate-limits.ts and src/lib/security.ts; tests/api/_harness.ts, which makes its own members.

### 8.32 Change management

Status: Partly.

Every change is a commit with a message saying what it does, and production only takes what is in version control. There is no change approval step and no release record.

Evidence: Git history.

### 8.33 Test information

Status: In place.

No production data is used for testing. The integration suite makes its own members through the real sign up endpoint and owns a random block of mobile numbers and CNIC numbers so a run cannot collide with anything else.

Evidence: tests/api/_harness.ts.

### 8.34 Protection of information systems during audit testing

Status: Not yet.

No audit testing has taken place. The rule for when it does is that it runs against a copy, not production.

Evidence: Open item.
